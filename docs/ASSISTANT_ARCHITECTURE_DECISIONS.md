## 当前技术基线（截至本稿所依据的交付报告）

- **硬件**：NVIDIA Jetson AGX Orin Developer Kit 64GB 统一内存；现场快照约 61 GiB 系统可用物理内存、约 52 GiB 空闲/可用内存。该数值随服务负载变化，不等同于独立 GPU 显存。
- **模型运行环境**：已报告 CUDA 12.6、JetPack 6.x、NVIDIA PyTorch 2.5.0、Transformers 4.57.6。Qwen3.5-4B 的真实加载与生成兼容性**尚未验收**。
- **现有视觉模型**：`Qwen3-VL-2B-Instruct`，回环模型服务通常为 `127.0.0.1:8010`。
- **Phase 1 后端**：`codex/assistant-backend`，交付提交 `7370e1c`；已报告实现 13 个 Assistant HTTP 接口、独立 `assistant.db`、消息轮询与生活事件管理；158 项 Python 测试通过、1 项跳过。测试使用隔离数据库/合成模型，不代表 Jetson 实机通过。
- **Phase 1 前端**：`assistant-frontend`，交付提交 `88d7d74`；已报告通过 Mock 前端测试，**真实前后端完整联调仍待验收**。
- **当前模型调度**：Phase 1 后端报告仍为 **Vision First**；本稿的 Chat First 是待实施的变更。
- **当前对外协议**：`POST /api/assistant/conversations/{id}/messages?scope=demo|real` 接受消息并返回 HTTP 202，客户端按 `poll_url` 轮询。**不存在已冻结的 `/api/assistant/chat` 对外接口**；SSE 不是当前 Assistant 协议的一部分。
- **数据范围**：Assistant 的 `demo/real` 与视觉的 `infant/adult_test` 是两套独立维度，任何查询都不能隐式混用。

## ADR-001：聊天优先与视觉新鲜度保护

**状态：Proposed（修订）**

### 决策背景

Nestory 是非医疗、非生命安全级育儿辅助应用。家长主动发起的聊天需要明确、及时的反馈；视觉分析属于周期性观察。现有 2B 视觉生成曾有约十几秒耗时的测试记录，但不能据此推断新模型或所有实际画面的固定延迟。

### 决策

1. **目标调度策略：Chat First + Bounded Vision Waiting**。模型空闲时若两类请求同时等待，优先聊天；但持续聊天不能让视觉无限期得不到处理。
2. **不假定正在生成的请求可抢占**。优先级默认仅在调度边界生效。只有目标推理运行时确实支持安全取消、且测试证明资源和状态清理可靠，才允许取消正在执行的视觉请求。
3. **视觉等待队列丢旧留新**。目标是最多保留一个尚未开始推理的视觉任务；新采样覆盖或取消旧的待处理任务。摄像头已有最新帧缓存不等于模型等待队列已具备覆盖能力，必须分别实现与测试。
4. **开始推理前检查画面新鲜度**。记录帧采集时间和开始推理时间；超出允许时效就重新取最新帧或丢弃请求。已过期结果不得当作当前状态写入时间线。
5. **视觉防饥饿**。定义可观测的最大有效观察间隔；超出阈值时，在当前不可抢占任务结束后优先处理视觉，再处理下一条排队聊天。候选阈值 120 秒，仅供实机数据校准，不应当作已验证保证。
6. **观察空档显式标记**。跳过、过期、模型繁忙、摄像头断开或服务不可用造成的间隔一律视为未知覆盖范围；不得把无观察推断为“持续睡着”或“状态未变化”。记录故障原因与覆盖情况，不记录私人图片内容到普通日志。
7. **有界资源保护**。继续限制请求队列、输入上下文、单次输出和超时。Phase 1 的聊天输出上限沿用契约的 `max_new_tokens <= 256`；将其放宽至 512 必须另行验证延迟并评估接口兼容性。
8. **前端协议不变**。Phase 1 仍使用 HTTP 202 + 轮询；前端立即显示 queued/running。SSE/流式文字和连续批处理仅列为未来可选优化，不作为当前集成前提，也不保证消除排队。
9. **监测指标**：聊天排队/完整响应的 P50、P95 和失败率；如果未来实现流式输出，再增加 TTFT；视觉推理时长、画面年龄、有效观察间隔、跳帧及未知覆盖时长。

**实施边界**：现有 Vision First 调度器及其测试暂作为 Phase 1 已交付基线；必须在独立分支完成本 ADR 的改造与回归测试，不能仅修改文档便声称已实现。

## ADR-002：双数据库隔离与统一时间线门面

**状态：Proposed（修订）**

### 决策

1. **保留两套 SQLite 数据库**。视觉数据库（通常为 `baby_monitor.db`）保存摄像头状态与观察；`assistant.db` 保存会话、消息和家长生活事件。具体文件路径以实际运行配置为准。分库的主要理由是数据生命周期、删除语义、故障隔离和独立备份；不声称 SQLite WAL 无法支持单库。
2. **明确写入所有权**。视觉业务管线经主应用视觉模块写视觉库；Assistant 服务经受控数据库层写 `assistant.db`。推理模型进程不能直接访问数据库或执行任意模型生成的 SQL、Python、Shell。
3. **统一只读门面**。优先扩展现有 `assistant_facts.py`，分别通过受限只读连接查询，再按统一 UTC 时间轴合并；不需要复制原始记录、也不要求跨库永久视图。
4. **标准化事件字段**至少包括：`event_id`（带数据源命名空间）、`scope`、`ts_start_utc`、`ts_end_utc`（可空）、`event_type`、`source`（`vision`/`parent_chat`/`parent_manual`）、`observation_mode`（适用时）、`confidence`（适用时）、`reliability`、`payload`。`recorder` 可选；没有明确身份信息不得虚构记录人。当前尚未实现多宝宝档案，不能把 `baby_id="default"` 视为身份隔离机制。
5. **时间单位规范化**。视觉库现有时间戳为 Unix 秒，Assistant 事件存储使用 UTC 毫秒；门面负责统一精度和时区转换。日期过滤按明确选择的 IANA 时区（默认 `Asia/Shanghai`）计算。
6. **不覆盖原始来源，不重复累计**。视觉“睡着”和家长报告的“睡着”可以并列保留；统计时人工睡眠内部重叠区间应取并集，人工与视觉时长不得直接相加。摄像头连续性未经验证时，视觉时长和完整睡眠次数不能作为确定值。
7. **严格范围隔离**。Demo 查询只读 Demo 生活事件，不接入真实视觉记录；Real 查询只读 Real 生活事件及 `infant` 模式视觉证据，排除 `adult_test`、`legacy_unknown`。
8. **查询范围受控**。工具通过参数化、预定义的 Python/SQLite 查询读取；不执行模型生成的任意查询。分页、时间跨度和证据条数遵循 API Contract 的上限；数据被截断时不得输出伪完整总数。
9. **按需注入 AI 上下文**。针对用户问题查询近期必要事件与后端计算后的汇总，而非无条件将过去 24 小时全部原始记录送入模型。查询例子包括喂奶汇总、已确认人工睡眠统计、带覆盖率提示的视觉观察和跨事件排序。
10. **实验性生理字段不视为已实现**。目前公开的视觉表结构没有经验证的心率/呼吸测量字段。未来即便新增，也须独立验证并默认排除出医学判断。

### 内部接口示意（不新增对外 HTTP 路由）

```python
def get_unified_timeline(
    scope: str,
    start_utc_ms: int,
    end_utc_ms: int,
    timezone: str = "Asia/Shanghai",
) -> list[TimelineEvent]:
    """按权限与来源汇总事件；返回可追溯且标注可靠性的时间线。"""
```

**实施状态**：Codex Phase 1 报告已具备部分跨库事实查询、人工睡眠区间并集和不可信视觉时长提示；完整多类型统一时间线及跨事件规律解释尚需单独验收。

## ADR-003：模型升级路线与逻辑双客户端

**状态：Proposed（修订；经批准后取代 v1 ADR-003）**

### 目标架构

**物理上一套模型服务，逻辑上两套独立客户端。**

```text
Nestory Web App
    |
    +--> Assistant HTTP API --> Assistant 客户端 --+
    |       (会话/记录/事实检索)                    |
    |                                               +--> 本地模型服务
    +--> 摄像头/状态机 ------> 视觉客户端 ----------+    /chat + /analyze
                                                        Phase 1: Qwen3-VL-2B
                                                        Phase 2: Qwen3.5-4B
```

- 两个客户端拥有各自的提示词、输入输出 Schema、token/图片参数、超时和错误处理。
- 配置上分别使用 `BMON_VLM_SERVICE_URL` 和目标新增项 `BMON_ASSISTANT_SERVICE_URL`。当前共享实例时均指向回环 `http://127.0.0.1:8010`；这项 Assistant 独立配置尚须核对/实现，**不能视为已有功能**。
- 模型服务仅绑定回环地址。前端不直接连接模型端口，只调用已冻结的 `/api/assistant/...` HTTP 接口。
- 共享实例仍需要 ADR-001 的有界调度。逻辑分开不意味着 GPU 推理可无冲突并发。

### 分阶段实施

**Phase 1：功能闭环（当前）**  
继续使用 `Qwen3-VL-2B-Instruct` 同时提供视觉 `/analyze` 和文字 `/chat`；优先完成 Codex 后端与 Gemini 前端的真实 API 联调、持久化、幂等、跨会话记录查询和安全边界。然后在单独改动中实现 ADR-001 的聊天优先/新鲜度保护，不把性能优化与基本功能联调混成一次无法定位问题的大改动。

**Phase 2：统一升级至 `Qwen3.5-4B`（原生多模态模型）**  
模型仍同时承担视觉与聊天，客户端和数据库不重写，对外 13 个 API 原则上保持不变。无需另做 Qwen3-VL-2B 与 3.5-4B 的大规模通用视觉跑分，但**必须进行兼容性与运行稳定性冒烟验收**：

1. 在独立 Python 环境验证 Qwen3.5-4B 的实际模型加载、图像处理、中文聊天、结构化 JSON 和关闭思考模式的请求行为；不直接覆盖已验证的 `.venv-models`。
2. 保证原 `/analyze` 输出字段和状态机语义、`/chat` 抽取动作与业务校验兼容；前端 API、聊天历史和生活记录无需迁移到新格式。
3. 在不影响正在运行的视觉服务的受控时段验证内存峰值、GPU 使用、异常恢复、聊天完整响应耗时、有效视觉观察间隔与连续运行稳定性。
4. 失败时保持可回退至已验证的 2B 服务与环境。不能仅依据官方通用视觉成绩声称婴幼儿睡姿或睡眠准确率达到某个百分比。

**未来可选：按性能瓶颈拆成两个实例。**  
仅在监测到长期无法接受的聊天等待或视觉观察间隔后，评估通过服务地址分流。两个模型实例仍共享同一 Jetson GPU、内存带宽与功耗，不保证完全互不影响。

### 初步验收指标（待实机校准）

- 聊天：记录队列等待、完整回复 P50/P95；首个可见前端状态应及时显示。TTFT <=5 秒只可作为未来流式服务的优化目标，不能作为当前非流式共享模型的硬性承诺。
- 视觉：候选有效观察间隔上限 120 秒；超限必须留下未知覆盖标记，不得隐瞒监测缺口。
- 稳定性：目标 24 小时无进程崩溃、OOM 或持续内存泄漏；内存余量建议至少保留约 10 GiB，但最终阈值由部署测试决定。
- 对外报告：公开基准分数只说明通用能力，不能替代婴幼儿实测准确率。

## ADR-004：决策治理与跨 Agent 协作

**状态：Proposed（修订）**

1. **版本化文档是项目事实基线**：架构、硬件状态、接口和实施记录保存在 `AGENTS.md`、`docs/` 及对应 Git 提交中。聊天和跨 Agent 记忆可辅助定位信息，但不保证完整、同步或始终准确。
2. **前置阅读**：Codex、Gemini、ChatGPT 在执行相关任务前检查适用版本的 `AGENTS.md`、API Contract 和已采纳 ADR，确认正在操作的仓库、分支与工作目录。
3. **用户审批**：Agent 可以建议或提交 Proposed 草案；只有项目所有者明确确认后才能将决策标为 Accepted。未经批准，不得擅自切换模型、改变对外协议、开放网络能力或部署生产版本。
4. **冲突优先级**：针对架构决策，已采纳且较新的 ADR 优于旧 ADR；对外 HTTP 协议以冻结的 API Contract 为准，变更须同步修订契约并通知两边开发者。实现现状由对应代码、测试和部署记录证明，不得由 Proposed 文档推定。
5. **隔离协作**：Codex 负责后端、模型和 Jetson；Gemini 负责前端、独立复核及经授权的公开脱敏发布；ChatGPT 协助需求与验收。分别在独立分支/worktree 操作，避免同时改同一工作目录。
6. **区分四种动作**：提交功能分支、合并内部 `main`、同步 Jetson 代码、重启/启用生产服务是不同步骤，后者须受变更审批和测试约束。`scripts/sync-jetson.sh` 只在符合其前提条件的内部 `main` 工作流使用，不自动覆盖任何工作区，也不自动重启服务。
7. **公开发布另行审查**：公开 GitHub 仓库与内部共享裸仓库可存在独立历史。发布前按 `docs/GIT_WORKFLOW.md` 和脱敏扫描流程检查，严禁上传私人记录、密钥、权重、媒体或内部部署敏感信息。

## ADR-005：离线时钟、时间戳与可信度

**状态：Proposed（新增）**

### 决策

1. **存储以 UTC 为基准**；Assistant 事件以 UTC 毫秒保存，视觉历史的 Unix 秒通过统一时间线门面转换。界面和“今天/昨天”的边界依据用户所选 IANA 时区计算，默认 `Asia/Shanghai`。
2. **启动及运行中检查时钟可信度**。综合合理时间下限、时间回退/大幅跳变、NTP/RTC 状态和最近校时信息判断；仅比较一个固定年份不能证明时钟准确。
3. **区分墙上时钟与单调计时**。同一次正常运行中的持续时间可使用单调计时器辅助衡量，但不得拿它跨重启构造日历时间。
4. **时钟不可信时不得制造可信记录**。对于依赖绝对时刻的事件，明确告知用户设备时间异常；“刚才”“半小时前”“今天”等相对说法不能在不可信时钟下自动确定日期。视觉缺口须记为不可信观察范围。
5. **拟新增持久化标记**：`clock_untrusted`、产生/校正状态及必要的审计字段须经过数据库迁移、读写兼容与测试后启用。在实现前，不得静默将不可信时间写成已确认的正常生活记录；应拒绝自动入库并提示人工补充可信时间。
6. **校时后不自动重写旧时间戳**。不可信期间的数据只有经过可追溯的人工更正或可靠重建后才能进入作息统计。
7. **离线保时**：先核查 Jetson 开发板 RTC、备用供电和系统服务配置，再决定是否需要额外电池或 RTC 设备；联网时继续使用 NTP 校时。

## ADR-006：联网、隐私与内容边界

**状态：Proposed（新增）**

1. **离线优先**。摄像头识别、本地 Qwen、生活记录、可用的作息统计和本地媒体在没有互联网时仍应工作；不能把云端 API 作为核心功能的默认依赖。
2. **本地数据边界**。婴幼儿身份、护理记录、对话正文、照片、视频、模型上下文和可识别的个性化摘要默认不得上传给外部育儿知识服务。
3. **外部知识检索属于独立可选功能**。默认关闭，经用户明确启用；每次出站请求可见、可审计。外发只允许经过检查的通用问题，不将孩子的个人记录自动改写成外部查询。系统 NTP 校时与自愿启用的知识检索分开管理。
4. **模型/工具安全隔离**。外部网页和检索结果均为不可信输入；读取这些内容的工具步骤不获得生活记录写入/删除权限。内容引用应标明出处、时间和适用范围，不生成未经证实的临床建议。
5. **断网降级透明**。离线时使用经核验的本地内容或缓存并标注来源及可能过期，不冒充新联网查询结果。
6. **媒体版权**。内置内容优先采用自制、获授权或可合法使用的素材；用户导入内容与应用分发内容分开管理。
7. **访问入口延续现有安全架构**。正常远程使用经回环主服务及 TLS/Tailscale 受控入口；可按现有配置明确开启受限的可信 LAN 预览，不能把其未加密 HTTP 当作公网安全入口。模型端口始终只绑定回环，不对 LAN 或公网直接开放。
8. **未来联网功能须单独审批**。本 ADR 不授权立即接入搜索引擎、爬取外部服务或改变现有监听地址。

## ADR-007：生活记录提取、智能确认与规律分析

**状态：Proposed（新增）**

1. **模型负责理解和结构化提议，后端负责事实校验与写库**。模型输出受限 Schema，不运行模型生成的 SQL。已确认的 Phase 1 事件类型为 `feeding`、`diaper`、`sleep`、`activity`。体温、用药是未来可能的扩展，尚未实现；涉及药物的字段、单位和确认策略需另行审批。
2. **采用智能确认，而非全部确认**：
   - 完整、明确且已经发生的事件，经过后端时间/语义/类型校验和事务提交后可以自动入库。
   - 时间、数量、对象或语义不明确时，显示 `needs_confirmation` 卡片，不猜测数值。
   - 更正和删除已有生活记录要求家长确认或显式的版本化表单操作；未来计划、否定或假设不写成已发生事件。
3. **时间解析由受控代码完成**。采用消息接收时刻 `reference_at` 与会话时区；“半小时前”等可确定的相对时长仅在时钟可信时由代码转换。“刚才”若不能精确确定时刻，就要求家长补充或确认；不得模型随意猜时刻。跨午夜和夏令时必须正确处理。
4. **只有数据库提交成功才能报告“已记录”**。入库、审计修订和回复状态保持事务一致；重复发送使用幂等 ID；更正/删除用 `expected_version` 防止覆盖。
5. **会话与生活事件独立**。删除对话会删除其消息/提议，但不会删除已保存生活事件。`source_message_id` 在消息删除后置空；生活事件只能通过其独立接口修改或删除，修订历史不得偷偷保存已删除聊天正文。
6. **跨会话事实检索**。新对话可访问同一 `scope` 内已确认、未删除的生活记录；聊天上下文仍以当前会话为界。Demo 和 Real 必须完全隔离。
7. **规律由后端计算**。例如喂奶总量、间隔中位数、人工睡眠区间并集和统一时间线排序；Qwen 只解释有来源、范围和可靠性标签的结果。没有足够数据就说明不足；不得叠加视觉与人工睡眠时长或编造完整日统计。
8. **非医疗边界**。不做诊断、用药处方或临床准确率保证；出现发热、呼吸异常等高风险描述时采用经过审查的就医/急救提示，不能仅凭摄像头推断临床状态。抽取流程默认尽量使用非思考模式；最终是否支持按请求关闭需随模型版本验证。
9. **Mock 不能冒充真实保存**。Mock 仅用于明确开启的开发测试。真实后端失败、404 或不可用时，正式界面必须提示失败，不得自动回落到内存 Mock 并向家长显示“已保存”。

### 端到端验收用例

1. 在 Demo 范围新建对话 A，输入“今天上午 11 点宝宝喝了 150ml 奶”。
2. 后端解析、校验并成功提交 `feeding` 事件，前端才展示 `saved`；若时间或语义不明则展示待确认卡。
3. 新建对话 B，询问当天喂奶情况；Assistant 使用同一 Demo 范围的已保存事件回答。
4. 返回对话 A，原历史仍在；删除对话 A 后消息消失，但喂奶事件仍可独立查询。
5. 单独删除喂奶事件后再次查询，不再计入统计。
6. 切换 Real 后不得看到 Demo 数据；未验证的视觉睡眠覆盖不得当作可靠总时长。
7. 重启应用后重复以上持久化、幂等、权限及审计检查；Mock 测试和真实 Qwen 测试结果分别记录。

| 里程碑 | 主要工作 | 验收标准 |

| M3：Jetson 实机验收 | 在受控时间测试现有 2B 共享模型与真实摄像头 | 记录聊天/视觉延迟、覆盖、内存、错误及中文提取表现 |
