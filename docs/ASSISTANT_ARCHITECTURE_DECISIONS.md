# AI Assistant 架构决策记录 (ADR)

本文档记录 Nestory (Baby Monitor) 项目在引入智能育儿助理 (AI Assistant) 过程中的核心架构决策，作为跨 Agent (Codex, Gemini, ChatGPT) 协作与系统演进的权威规范。

---

## 1. 决策背景与硬件运行基准

- **部署设备基准**：NVIDIA Jetson AGX Orin Developer Kit (64GB 统一内存版本，系统可用物理内存 ~61.0 GiB，日常运行空闲可用内存 ~52.0 GiB；CUDA 12.6, JetPack 6.x, PyTorch 2.5.0, Transformers 4.57.6)。系统时间与 NTP 已完成与标准时间（Asia/Shanghai, UTC+8）严格同步。
- **业务定位**：非医疗、非生命安全级家庭智慧育儿陪伴应用。核心价值在于提供连续的客观状态记录、情境化时间线整合及个性化育儿建议，而非毫秒级生命体征报警。
- **多 Agent 协作架构**：
  - **Codex**：主力后端与硬件部署工程师。负责推理服务、数据库操作、硬件资源适配及服务更新。
  - **Gemini**：前端工程、架构质量审查与文档规范负责人。负责 UI 开发、端到端测试、架构决策沉淀及公开代码库脱敏同步。
  - **ChatGPT**：产品需求定义与用户验收标准制定。

## 2. ADR-001：调度优先级反转与视觉采样队列“丢旧留新”机制

### 2.1 问题与痛点
在早期规划中，视觉分析任务被设为高优先级，文本对话排在视觉任务之后。但在实际运行时：
1. 单次视觉大模型 (VLM) 推理耗时通常在数秒至十几秒之间（2B 模型约 5~15s，更大模型耗时更长）。
2. 家长主动发起的 Assistant 聊天若排在视觉任务之后，会产生长达十数秒的无响应等待，造成严重界面假死感。
3. 视觉观察本质上是周期性定时采样（例如 15 秒至 60 秒抽样一次），抽样晚几秒或跳过某一单帧并不会对宝宝状态评估产生实质性安全后果。

### 2.2 架构决策
1. **调度优先级彻底反转**：
   - **Chat 对话请求赋予 P0 优先级（高优）**。
   - **视觉周期抽样赋予 P1 优先级（低优）**。
2. **视觉采样队列“丢旧留新”机制 (Latest-Only Drop Policy)**：
   - 视觉推理队列采用容量为 1 的单槽覆盖缓冲（Bounded Drop Queue）。
   - 当 GPU 正在处理聊天请求或前一帧推理时，新产生的摄像头采样帧直接覆盖旧的未处理帧；推理服务恢复空闲时，永远只取“最新的一帧”执行推理，积压的陈旧帧直接丢弃，不积压推理队列。
3. **对话请求保护与资源上限**：
   - 限制 Assistant 聊天生成的 `max_tokens`（建议 256 ~ 512 tokens），避免模型因长文本生成长时间占满 GPU 算力。
   - 采用 Server-Sent Events (SSE) 流式传输输出首字，将首字延迟 (TTFT) 压缩在可接受范围内。
4. **服务层运行时演进储备**：
   - 后续部署可评估引入支持连续批处理 (Continuous Batching) 与多 Slot 并发调度的服务层（如 vLLM 或 llama.cpp server），实现 Prefill 与 Decode 阶段的细粒度交错调度，彻底消除逐请求排队等待。

## 3. ADR-002：双数据库物理隔离与统一时间线门面层 (Unified Timeline Facade)

### 3.1 问题与痛点
系统存在两套数据来源：
1. `baby_monitor.db`：承载摄像头高频观察（睡眠状态、睡姿、表情、运动幅度、心率/呼吸估计等），写入频次高、生命周期自动化。
2. `assistant.db`：承载多轮聊天会话上下文、家长手动记录的日常护理事件（喂奶、换尿布、体温、用药等）及偏好配置。

若将两库强行物理合并，在 Jetson 本地 NVMe/eMMC 上容易因 SQLite 粗粒度写入锁（即使在 WAL 模式下高频并发写依然有锁争用）引发阻塞；但若完全物理孤立且缺乏互通层，AI Assistant 将无法获知客观视觉睡眠数据，无法回答“宝宝今天睡得好吗”、“距离上次喂奶宝宝睡了几觉”等需要结合视觉与护理的综合问题。

### 3.2 架构决策
1. **物理层保持物理隔离**：
   - 保持 `baby_monitor.db` 与 `assistant.db` 为独立的 SQLite 数据库文件。
   - 写入边界分明：视觉检测管线仅写入 `baby_monitor.db`；前端 Assistant 接口与护理记录仅写入 `assistant.db`。杜绝跨服务直接跨库乱写。
2. **逻辑层建立统一时间线门面 (Unified Timeline Facade)**：
   - 在后端数据访问层封装统一的事件读取接口（Unified Timeline Query Service 或使用 SQLite `ATTACH DATABASE` 提供只读视图）。
   - 提供标准化的时序聚合 API：
     ```python
     def get_unified_timeline(start_time: float, end_time: float, baby_id: str = "default") -> List[TimelineEvent]:
         """
         聚合读取 baby_monitor.db 的视觉睡眠/卧姿事件与 assistant.db 的手动护理事件，
         返回按时间戳全局正序排列的统一事件流。
         """
     ```
3. **AI 上下文与工具调用打通**：
   - Assistant 的 Context Builder 在组装系统提示词时，调用该门面注入近期（如过去 24 小时）的关键时序事件摘要。
   - Assistant 工具集（Tools）提供 `query_timeline(range, event_type)` 函数，由统一门面支撑数据检索，赋能大模型基于完整育儿时间线提供洞察。

## 4. ADR-003：硬件真实规格确认与 Qwen3.5-4B 分阶段演进路线

### 4.1 硬件真实规格核实
经过 Jetson 现场环境实际探测（`tegrastats` 与 `/proc/meminfo`）：
- **真实硬件**：NVIDIA Jetson AGX Orin 64GB 开发者套件（物理内存 61GiB 可用，系统空闲内存 ~52GiB）。
- **技术推论**：早期假定“硬件显存极度紧张无法支撑两模型共存”的假设已被事实推翻。52GB 空闲内存完全具备同时常驻两套 2B~7B 量化/半精度模型（单模型通常仅占 3~8GB）的物理承载力。

### 4.2 分阶段平滑演进路线
为保障开发节奏稳定，采取“两阶段演进”策略：

```
[Phase 1: 当前基线 - 单模型共用打通]
Web 前端 (Port 8000) ──> 后端 API (/api/assistant/chat) ──> Qwen3-VL-2B (Port 8010)
                                                    └─> 视觉周期分析 (Port 8010)
                                                    (验证单槽队列优先级与端到端链路)

[Phase 2: 目标架构 - 双模型独立服务]
Web 前端 (Port 8000) ──> 后端 API (/api/assistant/chat) ──> Qwen3.5-4B / 3.5-Text (Port 8020, 专属聊天)
Web 前端 (Port 8000) ──> 后端 API (视觉管线)             ──> Qwen3-VL-2B / 3.5-VL (Port 8010, 专属视觉)
                                                    (物理内存占用 ~12-16GB / 52GB 空闲，完全无抢占)
```

1. **第一阶段 (Phase 1: 当前基线联调)**：
   - 沿用当前部署的 `Qwen3-VL-2B-Instruct`（端口 8010）。
   - 由该服务同时支撑视觉抽样与初步的 Assistant 聊天请求。
   - 重点验证：ADR-001 的 P0 聊天优先与视觉单槽丢旧队列、前端 UI 流式打字与时间线展示。
2. **第二阶段 (Phase 2: 双模型解耦与 Qwen3.5-4B 独立服务)**：
   - 引入专用文本大模型：部署 `Qwen3.5-4B`（或 Qwen2.5-3B/7B 蒸馏版）作为专属聊天与推理模型，绑定于新端口（如 8020）。
   - 视觉模型独立：端口 8010 保持专用于视觉特征抽取与态势理解。
   - **前端零改造**：前端始终仅与后端 `/api/assistant/chat` 交互，由后端配置动态路由至 8010（Phase 1）或 8020（Phase 2），保持架构层面对前端代码的透明与平滑兼容。

## 5. ADR-004：跨 Agent 跨会话的项目持久化记忆与协作规范

### 5.1 痛点与记忆隔离
现代大语言模型 Agent 协作环境（Antigravity / Codex / ChatGPT）基于独立的上下文窗口运行。不同窗口、不同会话或多 Agent 实例之间不共享隐藏状态或会话记忆。若关键讨论成果仅停留在即时聊天中，在新的会话窗口中就会发生“失忆”，导致重复推演甚至推翻既定方案。

### 5.2 协作规范与持久化协议
1. **代码库文档即单一事实源 (Single Source of Truth)**：
   - 项目的所有硬件状态、架构决策、接口契约必须记录在代码库内（`AGENTS.md`、`docs/*.md`）。
   - 禁止依赖未落盘的聊天记录作为技术依据。
2. **跨 Agent 会话前置阅读规范**：
   - 任何 Agent 实例（Codex、Gemini、ChatGPT 等）在接手任务前，**必须首先读取 `AGENTS.md` 与相关 `docs/` 规范**，严格遵从既定角色职责与 ADR 决策。
3. **决策落盘与同步闭环**：
   - 凡在与用户对话中形成的架构变更、硬件校准或接口定义，必须由响应 Agent 立即编写/更新对应的文档并完成 Git 提交。
   - 涉及主干代码和文档的变更，须通过 `bash scripts/sync-jetson.sh` 广播至 Jetson 生产机，确保 Mac 与 Jetson 两端代码库的一致性与时效性。
